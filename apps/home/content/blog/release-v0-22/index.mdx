As of release v0.22 of the seedcord framework, Vite is now used as the build tool for both dev and production builds. In addition to bringing faster production builds with the usage of Vite 8 (Rolldown), this also ensures consistency between development and production. (Previously, we have been using `tsc-alias` for both type-checking and building bots)

To upgrade your bot, run your package manager's upgrade command:

```sh
npm upgrade --latest seedcord
yarn upgrade --latest seedcord
pnpm upgrade --latest seedcord

# Do the same with your transport package (i.e. @seedcord/gateway or @seedcord/http)
```

New to seedcord? Scaffold your first bot with our `create-seedcord` CLI:

```sh
npm init seedcord@latest
yarn create seedcord@latest
pnpm create seedcord@latest
```

Then head over to [our first bot guide](https://seedcord.org/guide/first-bot/).

Curious what seedcord does and why? [Start here!](https://seedcord.org/guide/)

Here are some things from this release we'd like to highlight:

## Static builds with Vite & Vite plugin support

As mentioned above, this release features Vite builds for production (`seedcord build`). Before, only `seedcord dev` was using Vite, which meant we had two different bundlers for dev and prod. As an additional pain point, the previous production build was more of a "transpilation", meaning that at runtime, your modules were still being dynamically read from the filesystem instead of statically imported.

By moving to Vite and unifying dev and build, we now have consistent parsing behaviour across dev and prod, as well as reduced complexity, and no more of that runtime module importing behaviour. Hooray for all!

Because we have now adopted Vite entirely, you can also use your own Vite plugins in the seedcord config file, like so:

```ts
import { defineConfig } from 'seedcord/config';
import { foo } from 'vite-plugin-foo';

export default defineConfig({
    // ...
    vitePlugins: () => [foo()]
});
```

Make sure that any environment-aware plugins target the `seedcord` environment, since that's the environment that seedcord is set up in.

You'll find other information about using Vite plugins, and when to use seedcord plugins vs Vite plugins, on [this guide page](https://seedcord.org/guide/build/vite-plugins/)

This upgrade, whilst already solving the bundling problems we had, also allows us to do something else that's pretty cool:

## Edge bots

You can now write HTTP bots that run on the edge (Cloudflare Workers)! Previously, the option to run bots on Workers wasn't functional, and you only had the option to run it on a server runtime like Node. With this release, you can now write bots using seedcord that build as Cloudflare Workers. These bots use Discord's Interactions webhook capability to allow your bot to receive certain events as a webhook call to your bot instead of via the Gateway, and when you're done, you can deploy them to the Cloudflare Workers platform.

To get started, run either of these commands (depending on your package manager):

```sh
npm init seedcord
yarn create seedcord
pnpm create seedcord
```

Then select the HTTP bots option.

![Bot transport options](./http-transport.webp)

And finally select Cloudflare Workers.

![HTTP bot runtime selection](./cloudflare-workers.webp)

Make sure to fill in the remaining details as requested, and then your bot should now be scaffolded.

> Note: The runtime option will only appear for edge bots.

Now, `cd` into your project directory:

```sh
cd edge-bot # replace with your bot's directory
```

And run `seedcord dev` with your package manager. Your bot will now be running and ready for you to iterate on. Edit a relevant file, and your bot will have hot module replacement (HMR) activating to swap out the module you just edited, faster than you can blink!

In dev, the bot is running inside `workerd`, the same runtime used by Cloudflare Workers. This ensures that there is minimal differences between your local testing and the production runtime. This is possible thanks to us moving to use Vite for both dev and build, allowing us to fully utilise the [Vite Environment API](https://vite.dev/guide/api-environment). This system allows us to coordinate dev and build in a separate runtime like this and accurately map the `seedcord` application. Huge thanks to the Vite team for making this!

Once you're ready to deploy, you can simply run this:

```sh
npx cf deploy --prebuilt
yarn exec cf deploy --prebuilt
pnpx cf deploy --prebuilt
```

Make sure you link your Cloudflare account, and voila! Now you've got a seedcord edge bot deployed to Cloudflare.

Read up on this in [the guide page](https://seedcord.org/guide/build/workers/).

## Command management via CLI

If you've ever deployed any bot to Discord (not just seedcord ones), you'll know that command management is a bit of a pain. There's no way to delete your registered commands in your console, neither for globally-registered or guild-registered commands.

That pain is no more for seedcord bots! Starting with this version, the framework CLI now has a `commands` subcommand, which is your home for managing command deployments.

Running `seedcord commands` gives you the following options:

![Command manager](./command-manager.webp)

- `Deploy the commands in your code` - seedcord will read your code, compile a list of commands, and deploy them according to how you configured your command (`guild` commands are deployed to a server of your choosing, `global` commands are deployed to the bot itself).
- `List the commands Discord has` - Obtains the list of commands that your bot has deployed in servers or globally.
- `Delete guild commands that duplicate a global command` - Dedupes any guild commands with the same name as any deployed global commands.
- `Delete every command globally or in guilds` - Deletes every command your bot has registered, glbally and/or in guilds. **This is very destructive, ensure that you are using the correct bot and targeting the correct guild!**

Each of these can also be accessed with subcommands:

- `deploy [options]`
- `list [options]`
- `clean [options]`
- `purge [options]`

This allows you to have simplified command management while building and maintaining your seedcord bot!

To learn more about the subcommands, visit [this guide page](https://seedcord.org/guide/tooling/commands/).

## Library mode

seedcord bots can be built (and published) as libraries! This allows you to write your bots using the framework, and export them for use as part of a larger application. This will be most useful to bots on HTTP transports, as you can easily integrate them into backend frameworks like Hono, H3, Elysia, or even full-stack frameworks like Nitro, TanStack Start, Astro, and more.

To build library bots, omit `build.start` from your seedcord config:

```ts
import { defineConfig } from 'seedcord/config';

export default defineConfig({
    root: './src',
    instance: './bot.ts'
});
```

And now, your bot will be packaged as a library, ready for you to reuse it elsewhere.

To use library bots, simply import them from their bot entrypoint:

```ts
import bot from '../bot'; // Change the entrypoint to your bot package entrypoint
```

HTTP bots comply with the `export default { fetch }` standard used by Cloudflare Workers, Bun, Hono, H3, Elysia, and more. This means that you can simply pass in one `Request` object and get the `Response` from the bot.

For Gateway bots, start them using the `start` method:

```ts
await bot.start();
```

Your bot can now be used like a library in another app.

See [the guide](https://seedcord.org/guide/build/package/) to learn more. There's also [a guide page on integrating with web servers](https://seedcord.org/guide/build/embed/).

## Session lock files

Do you ever forget about when you've already had a dev server started? Well, as a small new addition to this update, we've added a session lock file.

When you start a dev session, a lock file will be written to `{global temp folder}/seedcord-dev/<user-id>-<uuid>`, with the application ID that is being used. If another dev session starts with the same application ID, the CLI will throw an error, and letting you know that a dev session is already connected to that application.

![lockfile dev error](./session-lock.webp)

This will not trigger if bots are using different applications, so it won't get in your way if you are developing several distinct bots.
